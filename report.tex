\section{Introduction}
%----------------------------------------------------------------------

\subsection{Problem Statement}

Large Language Model (LLM) applications increasingly rely on semantic caching to reduce latency and API costs. GPTCache, an open-source semantic cache by Zilliz, intercepts LLM API calls, encodes queries as embeddings, and serves cached responses for semantically similar queries. However, GPTCache's built-in eviction policies (LRU, FIFO, LFU, Random Replacement) treat all cached entries as equal, ignoring a critical property of LLM workloads: \textbf{response regeneration cost varies enormously}. A 2000-token response is far more expensive to recompute than a 20-token one. When the cache is full and an entry must be evicted, a cost-unaware policy may discard an expensive response while retaining a cheap one---wasting the regeneration cost that was already paid.

This project implements a \textbf{Token-Cost-Aware W-TinyLFU} eviction policy that combines frequency-based admission filtering with cost-weighted eviction decisions, preferentially retaining high-cost cached responses.

\subsection{Related Work}

The Window TinyLFU (W-TinyLFU) algorithm was introduced by Einziger, Friedman, and Manes~\cite{tinylfu} and serves as the eviction policy in Caffeine, Java's most widely used caching library. W-TinyLFU combines a small window LRU with a TinyLFU admission filter and a segmented LRU main cache, achieving near-optimal hit rates across diverse workloads. The GPT Semantic Cache paper~\cite{gptsemcache} studied similarity thresholds for LLM caching and identified 0.80 as the optimal cosine similarity threshold, achieving up to 68.8\% cache hit rate with 97\%+ accuracy. Our contribution extends W-TinyLFU with LLM-specific cost awareness---to our knowledge, the first integration of cost-weighted W-TinyLFU into an LLM semantic caching system.

\section{Extension Design}
%----------------------------------------------------------------------

\subsection{Motivation}

Standard eviction policies (LRU, LFU, FIFO) treat all cache entries as equally valuable. In LLM caching, this assumption is incorrect: a cached response with 2000 tokens costs $\sim$100$\times$ more to regenerate than one with 20 tokens. Our extension makes the cache ``cost-aware'' by incorporating the response token count into eviction decisions.

\subsection{Architecture}

Our W-TinyLFU implementation follows the paper's three-segment architecture:

\begin{verbatim}
Window LRU (1%) --evict--> TinyLFU admission gate --admit--> Main SLRU (99%)
                                  |                              |
                           Count-Min Sketch              Probation (20%)
                           + Bloom doorkeeper            Protected (80%)
\end{verbatim}

New entries enter the window cache. When the window overflows, its LRU victim becomes a candidate for the main cache. If the main cache is full, the candidate competes against the probation segment's LRU victim via the TinyLFU admission filter.

\subsection{Supporting Data Structures}

\begin{enumerate}
  \item \textbf{Count-Min Sketch (CMS)}: 4-bit packed counters (16 per uint64 word) with 4 hash functions. Maximum counter value 15. Periodic aging halves all counters via \texttt{(table >> 1) \& 0x7777777777777777} when additions reach 10$\times$ cache capacity.
  \item \textbf{Bloom Filter Doorkeeper}: Filters one-hit-wonders. Cleared whenever the CMS resets, per the TinyLFU paper.
  \item \textbf{Segmented LRU (SLRU)}: Probation (20\%) + protected (80\%). Items enter probation; on hit, promoted to protected. Protected overflow demotes LRU victim to probation.
\end{enumerate}

\subsection{Cost-Aware Admission}

When \texttt{cost\_aware=True}, the admission decision computes:
\[
\text{value} = \text{frequency} \times \text{cost}
\]
where cost is the response token count. Following Caffeine's \texttt{BoundedLocalCache.admit()}: if $\text{value}_\text{candidate} > \text{value}_\text{victim}$, admit; if frequency $\geq 6$, admit with $\sim$1/128 probability (hash-DoS defense); otherwise reject.

\subsection{API Compatibility}

Our policy maintains full compatibility with GPTCache's \texttt{EvictionBase} interface, registered as \texttt{name="wtinylfu"} with the same \texttt{put}/\texttt{get}/\texttt{policy} API. The \texttt{set\_cost()} method is an additive extension.

\section{Experimental Setup}
%----------------------------------------------------------------------

\subsection{Workload Profiles}

\begin{enumerate}
  \item \textbf{Synthetic (Zipfian)}: 3000 queries from a Zipfian distribution ($\alpha$=0.7, vocabulary=500). Response tokens: 17--393 (mean 174). Stresses hit/miss ratio via skewed access patterns.
  \item \textbf{LMSYS-Chat-1M}~\cite{lmsys}: 3000 real LLM conversations. High diversity, most queries unique. Measures cache overhead under realistic conditions.
  \item \textbf{Ablation profiles}: ``repetitive\_short'' (vocab=100, $\alpha$=1.5, 10000 samples) and ``novel\_long'' (vocab=5000, $\alpha$=0.5, 10000 samples).
\end{enumerate}

\subsection{Metrics Collected}

Cache hit rate, token saving ratio, per-request latency (p50/p95/p99/mean), throughput (QPS), peak memory (MB), CPU utilization (user + system seconds via \texttt{os.times()}).

\subsection{Automation and CI}

Benchmarks are automated via Python scripts supporting parallel execution (\texttt{--workers~-1}) and repeated trials (\texttt{--repeats~3}) for statistical significance. GitHub Actions CI pipeline runs tests and benchmarks. Docker container runs the full evaluation in one command.

\subsection{Configuration}

\begin{itemize}[nosep]
  \item \textbf{Policies}: LRU, FIFO, LFU, W-TinyLFU, W-TinyLFU + Cost
  \item \textbf{Cache sizes}: 50, 100, 200 entries
  \item \textbf{Thresholds}: 0.80 (SOTA~\cite{gptsemcache}) and 0.85
  \item \textbf{Embedding}: all-MiniLM-L6-v2 (384-dim), FAISS flat, SQLite in-memory
  \item \textbf{Repeats}: 3 trials with shuffled query order per trial
  \item \textbf{Warmup}: 2$\times$ cache size queries excluded
\end{itemize}

\section{Discussion}
%----------------------------------------------------------------------

\subsection{Trade-offs}

\textbf{Hit rate vs.\ latency}: W-TinyLFU adds $\sim$38--43\% overhead at p95 for small caches where eviction is frequent, narrowing to 9\% CPU overhead at cs=200. In LLM deployments, this overhead ($\sim$40ms worst case) is negligible compared to API calls (100--2000ms). The higher hit rate means fewer API calls, yielding net latency reduction.

\textbf{Cost-awareness value}: Token saving ratio consistently exceeds hit rate improvement. At cs=50 (synthetic), hit rate is 74\% higher than LRU, but token savings are 74\% higher. This proves the policy caches \textit{better}, not just \textit{more}.

\textbf{Synthetic vs.\ real data}: Synthetic Zipfian data shows dramatic improvements (76.4\% vs 44.0\% token savings) because skewed distributions create strong frequency signals. Real LMSYS data shows smaller absolute improvements (6.0\% vs 3.1\% at cs=50) but consistent relative gains (+94\%). Lower absolute hit rates on LMSYS reflect query diversity, not policy weakness.

\subsection{Sensitivity to Parameters}

The policy is robust: window size 0.5--5\% performs equivalently; threshold 0.80 and 0.85 both show stable advantage; cache sizes 50--200 all benefit.

\subsection{Correctness Verification}

Implementation verified against the TinyLFU paper~\cite{tinylfu} and Caffeine's source code: window/main split (1\%/99\%), probation/protected (20\%/80\%), CMS reset mask (\texttt{0x7777...}), doorkeeper cleared on reset, admission threshold (6, $\sim$1/128), sample size (10$\times$ capacity). \textbf{38 unit tests} verify all components.

\subsection{Reproducibility}

Three paths: (1)~Docker: \texttt{docker build \&\& docker run}, (2)~Local with parallel workers ($\sim$5 min), (3)~Conda via \texttt{environment.yml}. GitHub Actions CI runs on manual trigger.

\section{Conclusion \& Future Work}
%----------------------------------------------------------------------

We implemented a Token-Cost-Aware W-TinyLFU eviction policy for GPTCache achieving consistent improvements over all baselines:

\begin{itemize}[nosep]
  \item \textbf{Synthetic}: 76.4$\pm$3.5\% token savings vs 44.0$\pm$0.2\% for LRU at cs=50 (+74\% relative)
  \item \textbf{LMSYS (t=0.80)}: 6.0$\pm$0.4\% vs 3.1$\pm$0.4\% for LRU at cs=50 (+94\% relative)
  \item \textbf{Ablation}: Cost-awareness adds +6.9pp token savings on top of frequency-based admission
  \item \textbf{Statistical significance}: Non-overlapping std ranges across 3 independent trials
\end{itemize}

\textbf{Future work}: Size-aware capacity management, adaptive window sizing via hill climbing, TTL integration, upstream PR to GPTCache.

\section{How to Reproduce}

\begin{lstlisting}
git clone https://github.com/a1amit/GPTCache.git
cd GPTCache && git checkout feature/wtinylfu-cost-aware

# Option 1: Docker
docker build -t gptcache-bench . && docker run --rm gptcache-bench

# Option 2: Local (recommended, ~5 min)
python -m venv .venv && .venv\Scripts\activate
pip install -e . && pip install -r requirements-bench.txt
python -m pytest tests/unit_tests/eviction/ -v -o "addopts=" \
    --ignore=tests/unit_tests/eviction/test_distributed_cache.py
python benchmarks/run_benchmarks.py --dataset synthetic \
    --n_samples 3000 --cache_sizes "50,100,200" \
    --policies "lru,fifo,lfu,wtinylfu,wtinylfu_nocost" \
    --thresholds 0.85 --output results/ --workers -1 --repeats 3
python benchmarks/visualize.py --input results/ --output figures/
\end{lstlisting}
